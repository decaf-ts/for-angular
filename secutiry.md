F1 — P1 — Vulnerability: user search term injected as fully-trusted HTML in EmptyStateComponent (OWASP A03 Injection, refleted XSS)
Sink: empty-state.component.ts:386 — return this.sanitizer.bypassSecurityTrustHtml(result as string); inside getSearchSubtitle(), called from ngOnInit (empty-state.component.ts:309) whenever searchValue is set. Rendered via [innerHTML]="searchValue ? searchSubtitle : subtitle" (empty-state.component.html:24).
Data flow: searchValue (empty-state.component.ts:235-236) is the end-user's search term (doc comment: "the search term that was used"). getSearchSubtitle(this.subtitle) calls ngx-translate instant(key, {'0': searchValue}) (NgxTranslateService.ts:21-23 — plain translateService.instant, no HTML escaping of interpolated params). The translated template, e.g. "No results for {0}", has the raw search term spliced in, and the result is then marked as trusted HTML, defeating the default sanitizer that every other binding in this package relies on.
Attack (statically demonstrated): app configures <ngx-decaf-empty-state subtitle="emptyState.searchSubtitle" [searchValue]="term"> with translation emptyState.searchSubtitle: "No results for {0}". A user searches for <img src=x onerror=alert(document.cookie)>. ngx-translate interpolates it unescaped into the string; bypassSecurityTrustHtml marks it trusted; Angular injects it into the <p> unfiltered → script executes in the app origin. This is the intended use of the searchValue feature (the doc comment for searchValue at lines 227-236 explicitly describes displaying the search term in the message), so no unusual app behavior is required.
Blast radius: full XSS in the hosting application's origin — session/token theft, actions as the victim, pivot to any same-origin surface. Every consumer app that renders user-typed search terms through this empty-state is exposed.
Severity vs exploitability: Severity P1 (OWASP A03, stored-ish reflected XSS in a published library). Exploitability high for apps using the search empty-state with an interpolation placeholder (the designed pattern); n/a otherwise.
Fix (concrete): in getSearchSubtitle (empty-state.component.ts:386), replace bypassSecurityTrustHtml(result) with this.sanitizer.sanitize(SecurityContext.HTML, result) wrapped as SafeHtml (or simply return the plain translated string and let the default-sanitized [innerHTML] binding sanitize it — the binding already does this for the non-search path). Optional defense-in-depth: HTML-escape searchValue before passing it to instant (contextual output encoding at the interpolation site).
Residual risk: Angular's sanitizer still permits benign markup in translations; a compromised translation file remains a trusted-code channel (that trust boundary should be documented for consumers). Regression test required per review bar: case with searchValue = '<img src=x onerror>' asserting the rendered subtitle contains no onerror/<img> — this test must fail against the current code.
F2 — P2 — Conditional / hardening debt: modal bypassSecurityTrustHtml on developer-supplied inlineContent
Sink: modal.component.ts:351-357 (parseInlineContent()), rendering at modal.component.html:78 and :99. Public helpers route straight into it: getNgxInlineModal(inlineContent, …) (modal.component.ts:555), lightbox variant (:568-575, default '<div></div>').
Data flow: inlineContent?: string | SafeHtml (modal.component.ts:177) is caller-supplied. A string input is bypassed unconditionally (:356) — no sanitization, no documentation of the trust contract. HTMLElement input is serialized via outerHTML and bypassed (:354).
Exploitability: today this is developer-trusted-HTML-by-design, so it is not directly exploitable by end users — unless any consumer passes user-derived data (model field, URL param, message template) as inlineContent, which the API actively invites since it accepts plain strings. One careless caller converts this into the same XSS class as F1. Card's equivalent inlineContent (card.component.html:28,34) stays default-sanitized — the inconsistency itself is evidence the modal bypass is not a deliberate, documented trust boundary.
Severity: P2 (conditional vulnerability / insecure default). Exploitability: depends on consumer misuse; library ships the unsafe primitive.
Fix (concrete): drop the bypassSecurityTrustHtml on the string branch (:356) — bind the raw string and let Angular sanitize, matching card's behavior; for HTMLElement (:354), either serialize-then-sanitize or restrict to SafeHtml input only. If raw-HTML support is intentionally kept, gate it: accept only pre-sanitized SafeHtml from callers and document the trust boundary in the JSDoc of getNgxInlineModal/getNgxLightboxModal.
Residual risk: removing the bypass may break consumers who legitimately pass trusted HTML; ship as a minor with a migration note. Regression test: render a modal with inlineContent = '<img src=x onerror>' and assert sanitized output.
F3 — P2 — Conditional: un-sanitized raw SVG injection in NgxMediaService.loadSvgObserver
Sink: NgxMediaService.ts:323 — target.innerHTML = svg; after http.get(path, {responseType: 'text'}) (:316-324), executed runOutsideAngular (:317), so the Angular sanitizer never sees it. Called from svg.directive.ts:88, and from the icon component (icon.component.html:66,122 route via ngx-decaf-svg).
Data flow: the path comes from the name input of ngx-decaf-icon (icon.component.ts: type='image', isSvg when name ends .svg) or the directive input / host src attribute (svg.directive.ts:88-90). HttpClient fetches any URL (relative or absolute). The fetched text is written into the DOM raw. SVG inlined via innerHTML executes <script> elements and on\* handlers inside it — unlike <img src=x.svg>, which would have been inert.
Exploitability: conditional. Same-origin bundled sprites (the default assets/tabler-sprite.svg, icon.component.ts:80) are fine. But any consumer that passes a remote/user-influenced path (CDN host, user-uploaded avatar SVG served from the app origin, query-param-derived name) gets attacker-controlled script execution. Serving user-uploaded SVGs is common, and SameSite/CSP does not stop same-origin inline SVG script. Also a browser-side SSRF-lite primitive (fetch arbitrary URLs with app cookies) when path is user-controlled.
Severity: P2 (conditional vulnerability in a published library). Exploitability: high given user-influenced path; nil for default sprite usage.
Fix (concrete): in loadSvgObserver, sanitize before injection: target.innerHTML = this.sanitizer.sanitize(SecurityContext.HTML, svg) ?? '' (Angular's HTML sanitizer keeps SVG shape, strips scripts/handlers), and reject absolute/cross-origin paths unless explicitly allowlisted. Fix the class, not the instance: put the sanitization in the service so every caller (directive, icon) inherits it.
Residual risk: sanitizer-permitted SVG constructs can still alter layout/steal focus; a documented same-origin-only policy is the durable boundary.
F4 — P3 — Informational/hardening: tooltip denylist tag-stripping regex
tooltip.directive.ts:87 strips tags with replace(/<[^>]+>/g, '') (denylist-style, defeated by malformed input like <img src=x onerror=... fragments), but both final sinks are safe: renderer.createText(...) (tooltip.directive.ts:92,95) creates text nodes, and truncate.pipe.ts:17 sanitize feeds only that path. The setProperty(element, 'innerHTML', '') at tooltip.directive.ts:86 writes an empty string only. Not exploitable as written — flagging only because the regex looks like a sanitizer and a future refactor might reuse it where the sink is HTML. Remedy: comment the helper as "display-only, not a security control" or rely solely on createText.
F5 — P3 — Hygiene: misleading security documentation + dead sanitizer
modal.component.ts:351-353 doc claims "Normalizes and sanitizes inline modal content … safely trusts" and empty-state.component.ts:376-380 mermaid claims "Return sanitized SafeHtml" — both describe bypasses that perform no sanitization. Documentation that misstates the security property is how F1/F2 survive review. Fix the wording when fixing F1/F2.
file-upload.component.ts:280 injects DomSanitizer but never uses it (dead code) — remove or actually sanitize preview URLs if that was the intent.
Preview ion-img [src]="previewFile" (file-upload.component.html:87-88,235-236, values from FileReader data-URLs or persisted source values at file-upload.component.ts:683-686) stays on Angular's default URL sanitization — javascript: and unsafe schemes are rejected; safe as-is.

What to tell library consumers (requested)
Treat inlineContent on modals and getNgxInlineModal/getNgxLightboxModal string inputs as trusted HTML — never pass end-user-derived data; prefer SafeHtml you sanitized yourself, or wait for the F2 fix.
Any app using ngx-decaf-empty-state with searchValue + a {0} placeholder in the subtitle is exposed to F1 today — until the library fix ships, either drop searchValue, pre-escape it in a computed property, or override searchSubtitle with pre-sanitized content.
Do not point ngx-decaf-svg/icon name at user-uploaded or cross-origin SVGs until F3 ships; serve only bundled, same-origin sprites.
